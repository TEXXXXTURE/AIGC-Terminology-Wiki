## 定义

上下文窗口（Context Window）是模型一次能「看到」的最大 token 数，相当于它的工作记忆大小：输入提示词、检索到的资料、加上已经生成的回答，全部算在这个窗口里。超出窗口的部分会被截断、或者被模型「遗忘」——所以窗口大小直接决定了一个模型能处理多长的对话、多大的文档。

## 原理

窗口按 token 计，因此同一段文字在不同 [Tokenizer](../../02-组件/Tokenizer.md) 下占的窗口大小可能不同。窗口为什么不能无限大？根源在[注意力机制](../../01-底层原理/注意力机制.md)：标准注意力的计算量随序列长度平方增长（O(n²)），序列翻一倍、算力要四倍；同时长上下文要缓存每个 token 的 Key/Value 向量（KV Cache），显存占用随长度线性膨胀。两头一夹，长窗口就成了「又贵又慢」的奢侈品。

## 由来与历史

早期模型的窗口小得可怜：BERT 只有 512 token，GPT-2 是 1024。之后窗口一路膨胀：GPT-3 的 2048、GPT-4 的 8K/32K、Claude 与 Gemini 的 200K/1M、Qwen 的百万 token 版本。这背后是一连串技术接力：RoPE 等更好的位置编码、FlashAttention 降低显存读写开销、稀疏注意力与滑动窗口近似、以及 KV Cache 压缩——把 O(n²) 的代价一点点压下来。

## 应用

长窗口的直接价值是「整本书、整份代码库、超长对话」都能一次塞进去。但代价很现实：显存占用陡增、生成变慢、API 按 token 计费于是成本飙升。实用建议：不是所有任务都需要把窗口拉满——精确问答用 RAG 检索更划算，只有需要全局理解的精读任务才值得吃长窗口的成本。详见 [RAG](RAG.md)。

## 争议 / 讨论

「窗口是不是越大越好」一直有争论。乐观派认为窗口还在快速变大、终将「无限长」；怀疑派则指出两个硬约束：一是注意力 O(n²) 的算力墙和 KV Cache 的显存墙依然存在；二是「lost in the middle」——研究表明模型对窗口中间位置的注意力天然更弱，塞得多不等于用得好。所以近年的方向从「纯堆长度」转向「更长 + 更会检索 + 更会压缩」的组合。
